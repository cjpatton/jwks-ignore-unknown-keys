# JWKS ossification tests

Everything here except this README is generated by `../generate.py` from the inputs in
`../testdata/`.

- `cases.json`: manifest of cases with the JWK Set file, the token to verify, description, RFC rule,
  and expected result. Paths are relative to this directory.
- `<case-id>.json`: one JWK Set per case. Each lists the odd key(s) first and `rsa-1` last.
- `token.jwt`: RS256 JWT, header `kid: rsa-1`, expires 2100-01-01.
- `token-nokid.jwt`: the same JWT with no `kid` in the header.
- `rsa-1.public.pem`, `rsa-1.public.jwk.json`: the signing key.

**Every case is expected to verify its token.** A library that rejects a set is failing to
ignore something RFC 7517 says it should ignore.

| Prefix | What is unusual | RFC 7517 |
|---|---|---|
| `00` | Nothing (harness sanity check) | |
| `A` | AKP keys: pure ML-DSA (RFC 9964) and the 7 composites from draft-ietf-jose-pq-composite-sigs-06. Public keys come from `../testdata/vectors/`. | §5 SHOULD ignore |
| `B` | Unknown `kty` | §5 SHOULD ignore |
| `C` | Known `kty`, unsupported `crv` / `alg` / size | §5 SHOULD ignore ("out of the supported ranges") |
| `D` | Known `kty`, missing required member | §5 SHOULD ignore |
| `E06`-`E07` | Another key has an unregistered `use` / `key_ops` value (`https://example.com/jwk/future`). Rejecting that key is fine; rejecting the set is not. | §5 SHOULD ignore ("out of the supported ranges"); §4.2 / §4.3 allow other values |
| `N00` | Token without `kid`, set with only `rsa-1`. Fails if the verifier requires a `kid` at all, which is a separate limitation from the one this suite targets. | §4.5 `kid` is OPTIONAL |
| `N01` | Token without `kid`, same set as `Z01`. The verifier can't jump straight to `rsa-1`, so it has to cope with every other candidate key. Only meaningful if `N00` passes. | §4.5 `kid` is OPTIONAL; §5 |
| `Z01` | All of the odd keys above in one set | |
